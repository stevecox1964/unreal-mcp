## Dependency graph (who blocks whom)

```
#1 named-place resolver ──────────────┬──────────────► #5 social-goal hooks ("go to <person/place>")
  (offline, self-contained, no deps)  │                 (#5 episodic/social/consolidation are independent of #1)
                                       └──────────────► #4 first loop target (4.4)

#3 runner (factory → sim_runner → control API) ──┬──► #2.5 / #3.5 web controller (start/stop/status)
  (large; iter-2 2.1–2.3; NOT built yet)         └──► #4 *live-sim* autonomy (build/test loop needs neither)

#2 settings page (2.2 config_store → 2.3 page → 2.4 provider toggle) ── independent of #1/#3
  └─ 2.1 rename is independent of everything

#4 harness (4.1 contract, 4.2 preflight, 4.3 aggregator) ── independent; gated for *live* work by #3 + local models

Child BPs (Next up) ── editor + design choice; NOT loop-safe; independent
```

**Reading it:**
- **#1 is the keystone** — zero deps, offline-testable, and it unblocks both #5's social-goal hooks and #4's first real target. Highest leverage per unit work.
- **#3 is the long pole** — nothing in it exists yet (`factory.py`/`sim_runner.py` confirmed absent), and it gates the web controller (#2.5/#3.5) *and* live-sim autonomy (#4). Everything "overnight" routes through it.
- **#5's storage layers** (episodic, social, consolidation) are independent of #1; only the *social-goal hooks* need #1's resolver to turn "greet Maren" into a navigation target.
- **#2 and #4-harness are independent** and can fill parallel capacity, but neither is on the overnight critical path.

## Recommended build order

1. **#1 named-place resolver** — keystone, offline, smallest, unblocks the most. Do it first (it's also #4's
   designated first loop target, so doing it validates the harness premise).
2. **#5 episodic + social store + consolidation** — independent of #1; the "remembers who it met" half of the
   MVP. Social-goal *hooks* come after #1 lands (they need the resolver).
3. **#3 runner (2.1 → 2.2 → 2.3)** — the long pole; start it early in parallel since #1/#5 don't depend on it,
   but it's the gate for "overnight." This is the big lift.
4. **#2.5 / #3.5 web controller** — once 2.3's control API exists, the web app can drive start/stop/status.
5. **#2 settings page + #4 live autonomy** — quality-of-life and process, after the MVP loop closes.

**Parallel tracks** (independent, can run concurrently): {#1 → #5} · {#3 runner} · {#2.1 rename + #2 settings}
· {#4 harness 4.1–4.3, which can be built and even *exercised on #1* before #3 exists}.

## Cross-cut observations (things only visible across themes)

- **#4's harness can be built before its blocker.** 4.1–4.3 (contract, preflight, aggregator) are pure
  Python/offline and #1 is a live target for them *today* — so #4-the-harness need not wait on #3/local models;
  only #4-running-the-live-sim does. Decouple those two in the backlog.
- **The "how observations save to cells" subtask is shared** between #1 (grid/place cells) and #5 (episodic
  records attach to place cells). Design it **once**, in #1, and have #5 build on it — don't solve storage twice.
- **#2 and #3 share the web app** (already noted) — but #2.1 rename and #2 settings have **no** runtime
  dependency on the runner; only the controller panel (#2.5/#3.5) does. Ship rename + settings without waiting on #3.
- **Cost gating is real and narrow:** only *live-sim* execution burns per-tick inference credits. #1/#5 unit
  work, #4 harness, #2 UI, and #3 plumbing are all cheap (no/low LLM calls) — safe to do on cloud now; reserve
  local-models for the overnight *runs*.
